## 0. ⚠️ Главные правила работы с этим проектом (прочитать первым!)

> Это самые важные договорённости по коду. Соблюдать обязательно.

### 0.1. Комментировать только действительно важное

- Комментируем **редко и по делу** — только те места, которые реально помогут
  новому разработчику понять неочевидное: нетривиальные формулы, нестандартные
  форматы (`asset`-строки, единицы, смещения), порядок вызовов, подводные камни.
- **Не** комментируем очевидное (`// increment i`, `/* get user */`) и **не**
  дублируем в комментарии то, что и так ясно из имени функции/переменной.
- Комментарий объясняет **почему**, а не **что**. Если код можно сделать понятнее
  без комментария — делайте код, а не комментарий.
- Старые неуместные/шумные комментарии — удалять, а не множить.

### 0.2. Никаких юнит-тестов

- **Юнит-тесты не пишем** и инфраструктуру под них не заводим.
- Вместо них — **только e2e-тесты**, проверяющие систему целиком (см. §0.3).
- Существующий `tools/mongotest.py` юнит-тестом не является (это интерактивный
  деструктивный скрипт, требует флаг `--run`) — см. «Известные проблемы».

### 0.3. E2E-тесты — после каждого крупного тематического блока правок

- После **каждого крупного тематического блока правок** — прогонять **e2e-тест**
  (если это возможно).
- «Крупный тематический блок» = завершённая группа изменений по одной теме
  (например: конфиг; безопасность; торговое ядро; рыночные данные; фронтенд).
- «Если возможно» — если блок правок вообще поддаётся проверке сквозным сценарием.
  Правки, которые нельзя проверить end-to-end, не блокируют работу, но это надо
  явно отметить в описании блока.
- Готовый e2e-скрипт: **`tests/e2e.py`** (см. §0.3.1). Он поднимает клиентов
  через HTTP и прогоняет сценарий **регистрация → баланс → выставление ордера →
  матчинг → лента**; отдельные HTTP-примеры — в `docs/RUNBOOK.md` §8.
- Цель — не покрытие, а уверенность «сценарий целиком не сломан» после правок.

### 0.3.1. Обязанность ДОПОЛНЯТЬ `tests/e2e.py`

> ⚠️ **Это требование к каждой крупной правке, а не рекомендация.**

- `tests/e2e.py` — **общий, живой e2e-тест проекта**. Любой агент, закрывший
  крупный тематический блок, **обязан дополнить его** проверками, покрывающими
  именно свои изменения (новый роут, новая логика матчинга, новое поле ответа,
  новый источник данных и т.п.), и оставить тест **зелёным**.
- **Не удаляйте и не ослабляйте** существующие проверки ради «зелёного» прогона.
  Если проверка стала неактуальной из-за намеренного изменения поведения —
  обновите её ожидание и явно напишите об этом в `docs/DONE.md`.
- Тест должен оставаться **детерминированным**: он создаёт собственных
  пользователей со случайными ключами и в начале сбрасывает `orders`/`contracts`
  (см. `reset_exchange_state()`, отключается `E2E_RESET=0`). Зависимость от
  оставшихся от прошлых прогонов ордеров — источник ложных падений.
- При изменении структуры данных (например, задача #17 — регенерация серий)
  обновляйте константу `ASSET` в тесте на актуальную серию.
- Запуск (при поднятом стеке и API, см. §7):

  ```bash
  docker compose up -d
  PY_MODE=dev python api/app.py &     # API на :6969
  .venv/bin/python tests/e2e.py       # адрес API берётся из API_URL
  ```

  Скрипт печатает список проверок и завершается кодом `1` при первом провале.

## 1. Что это такое

**YZoZ** — демонстрационная (α-версия) криптобиржа **опционов** на пару **ETH/BTC**.
Не реальные деньги: после регистрации пользователь получает виртуальные
**1000 Wei** и **100 000 000 Satoshi**. Пользователи выставляют лимитные ордера на
покупку/продажу европейских опционов Call/Put по страйкам, система автоматически
сводит (матчит) встречные заявки, ведёт позиции (контракты) и считает P/L.
Теоретическая цена опциона считается по модели Блэк–Шоулза.

Проект написан примерно в 2017–2018 гг. и сейчас находится в состоянии
**заброшенного прототипа**: последний коммит — 23 января 2018.

## 2. Технологический стек

| Слой | Технологии |
|---|---|
| Веб-фронтенд | Node.js, Express, Pug (шаблоны), jQuery / jQuery UI, LESS (стили) |

| Хранилище (история) | InfluxDB 1.x — «river» ордеров и сделок |
| Кэш/ускорение | Memcached — цены, волатильность, теоретические цены, состояние |
| Расчёты | numpy, scipy, pandas, matplotlib (графики) |
| Планировщик | `api/theo.py` — отдельный долгоживущий сервис (`schedule`), пересчитывает PRICE/THEO/HV |
| Оркестрация | `make up/down/logs/e2e/check/lint/format` (+ `Procfile`, + compose-профиль `app` — весь стек в контейнерах) |
| Качество кода | ESLint + Prettier (JS), ruff (Python), `.editorconfig` (задача #27) |

### 3.3 Кто за что отвечает (по файлам)

- **`app.js` / `bin/www`** — только веб-слой. `bin/www` создаёт HTTP(S)-сервер;
  в `production` дополнительно слушает 80 и редиректит на HTTPS, читает TLS-сертификаты
  Let's Encrypt из `/etc/letsencrypt/live/yzoz.com/`.
- **`routes/exchange.js`** — читает каталог через сервис `lib/instruments.js`
  (разбор `exchange/instruments.json` вынесен из роута, задача #23), находит по
  `token/unit/exp` нужную серию и её страйки, рендерит `views/exchange.pug`.
- **`lib/instruments.js`** — сервис каталога инструментов веб-слоя:
  `load`/`instrument`/`firstExp`/`series`. Путь к файлу — от корня репозитория.
- **`api/inc/state.py`** — сборка производных рыночных ответов API (`/state`,
  `/best`, `/last`, `/theo`) из Memcached-ключей и каталога (#23). Соединений не
  держит: каталог и getter передаются аргументами.
- **`routes/health.js`** — healthcheck веб-слоя (`GET /health`, задача #24):
  опрашивает API-`/health` и отдаёт `{"status", "web", "api"}`.
- **`api/app.py`** — все REST-маршруты. При старте **один раз** строит каталог
  активов через `inc/mc.py:loadCatalog()` и вызывает `rebuildCache()` — пересборку
  `PRICE/HV/LAST/BEST/THEO` из Bybit и Mongo (задача #19; Memcached не переживает
  рестарт сервисов).
- **`api/theo.py`** — планировщик как **отдельный сервис** (задача #18): раз в
  минуту `setCurrent`+`setTheo`, раз в 15 минут `setHV`, при старте —
  `loadCatalog()`+`rebuildCache()`. Режим `--once` — разовый пересчёт. Общий
  Memcached с API.
- **`api/inc/trade.py`** — «мозг» биржи: `sendOrder()` решает, лимитка это или матч,
  и вызывает `makeDeal`/`removeOrder`/`editQuant`.
- **`api/inc/users.py`** — расчёт балансов: собственные средства, залоченные под
  ордера/контракты, реализованный и нереализованный P/L.

## 4. Доменная модель

### 4.1 Формат идентификатора опциона (asset)

Строка, разделённая `_`:

```
TICKER  _  EXP       _  STRIKE  _  TYPE
ETH_BTC  _  1793491200 _  50000  _  C
 └─база └───unit      └─ unix-время экспирации (сек)
                                  └─ C = Call, P = Put
```

Например: `ETH_BTC_1793491200_50000_C`. Разбор выполняет `inc/utils.py:splitAsset()`.

### 4.2 Инструменты (`exchange/instruments.json`)

```json
[{
  "ETH_BTC": {
    "name": "Ethereum/Bitcoin",
    "size": "1 Wei",
    "measure": "1 Satoshi",
    "series": [{ "1793491200": { "strikes": [60000, 55000, 50000, ...] } }]
  }
}]
```

- Одна серия = один момент экспирации (`exp`).
- Задача ТЗ **#17** регенерировала серии: сейчас их **три, в будущем** (ноябрь и
  декабрь 2026, январь 2027), страйки `10000…60000` с шагом 5000 вокруг текущей
  цены ETH/BTC (~30000 Satoshi). Раньше была единственная истёкшая серия
  `1519862400` (март 2018).
- При старте API из этого файла разворачивается полный список активов
  (для каждого страйка — Call и Put) через `inc/mc.py:loadCatalog()`.

### 4.3 Числовая модель и единицы измерения (задача #31)

Денежные величины в системе — **целые числа**, дробных значений нет. Это важное
соглашение: `quant`/`price`/`amount`/балансы — целые; любое деление округляется
(`int(round(...))`), а не хранится как float.

| Величина | Единица | Тип | Примечание |
|---|---|---|---|
| `quant` (объём) | контракты | int (целое) | > 0; объём позиции может быть отрицательным (short) |
| `price` (цена опциона) | **Satoshi** | int | за 1 контракт; > 0 |
| `amount` (`price × quant`) | **Satoshi** | int | знак повторяет знак `quant` (см. `makeDeal`) |
| баланс `ETH` | **Wei** | int | при регистрации 1000 |
| баланс `BTC` | **Satoshi** | int | при регистрации 100 000 000 |
| `PRICE_<TICKER>` | Satoshi | int | сырая цена базового актива **× 1 000 000** |
| `strike` | Satoshi | int | из каталога, строка → `int()` |
| `time` (заявки/сделки) | **микросекунды** | int | `getTime()`; см. ниже |

- **`price × 1_000_000`.** Кэш `PRICE_<TICKER>` (`inc/mc.py:setPrice/setCurrent`)
  умножает цену ETH/BTC на `1e6`, чтобы хранить её целым числом без потери
  точности. Все потребители (`theo`, фронт `getCounters`) трактуют это значение
  как Satoshi×1e6; при показе цена не делится (историческое поведение стола).
- **`getTime()` = микросекунды.** `inc/utils.py:getTime()` возвращает
  `int(time.time() * 10_000_000 / 10)`, т.е. `time.time() * 1e6`. Это целое
  (unix-микросекунды). Хранится в `orders.time`, `contracts.time` и в
  STATE-метках. Фронт делит на `1000` в `convertDate` (историческая схема:
  значение трактуется как миллисекунды) — деталь отображения, на сортировку в
  Mongo (`$sort: {time: 1}`) не влияет, т.к. монотонность сохраняется.
- **Проверки диапазонов на входе** (`api/app.py` `/order`): `quant > 0` и
  `price > 0` — иначе `400`; `quant`/`price` приводятся к `int`
  (`int()` → при мусоре `400 Bad Quantity or Price`). Те же проверки —
  в ветке `edit`. `theo()` (`inc/calculation.py`) сам гарантирует
  `S>0, K>0, V>0, T>0`, иначе возвращает внутреннюю стоимость.
- **Защита от деления на ноль.** Везде, где считается средняя цена
  (`amount / quant`): `inc/contracts.py` (`userContracts`, `userTrades` —
  при `quant == 0` цена `0`, задача #29), `inc/users.py` (`realisedPL`,
  `clearContracts`) — ветки `quant == 0` обработаны явно. `setLast()`
  пропускает закрытые позиции (`quant == 0`).

### 4.4 Модель данных

**MongoDB (БД `exchange`)**

| Коллекция | Назначение | Ключевые поля |
|---|---|---|
| `users` | Пользователи | `hash` (blake2b ключа), `seed`, `passwordHash`, `passwordSalt`, `email`, `balances`, `time` |
| `orders` | Открытые заявки | `user`, `type` (buy/sell), `asset`, `quant`, `price`, `time`, `ticker`, `exp`, `strike`, `dude` |
| `contracts` | Исполненные сделки / позиции | `user`, `quant` (±), `amount`, `asset`, `time`, `ticker`, `exp`, `strike`, `dude` |

**InfluxDB (БД `orders` и `trades`)**

- `measurement` = тикер (напр. `ETH_BTC`), `tag exp` = время экспирации.
- Поля: `user`, `type`, `quant`, `asset`, `price`, `action` (orders) / `oppUser` (trades).
- Используется для «river» — ленты последних ордеров/сделок (LIMIT 100, ORDER BY time DESC).

**Memcached — схема ключей** (см. `api/inc/mc.py`)

| Ключ | Значение |
|---|---|
| `PRICE_<TICKER>` | цена базового актива (×1e6) |
| `HV_<TICKER>` | историческая волатильность |
| `THEO_<TICKER>_<EXP>_<STRIKE>_<C\|P>` | теоретическая цена по Блэку–Шоулзу |
| `LAST_<ASSET>` | цена последней сделки |
| `BEST_<SELL\|BUY>_<ASSET>` | лучшая цена в стакане |
| `STATE_<TICKER>_<EXP>_<TRADE\|ORDER>` | «метка» изменения, фронт по ней решает, обновлять ли стол |
| `TICKERS`, `ASSETS`, `CURRENCYS` | справочники (списки) |
| `<TICKER>_SERIES`, `<TICKER>_<EXP>_STRIKES` | серии и страйки тикера |

> ⚠ Memcached здесь — **не только кэш**, но и единственный источник истины для
> `BEST_*`, `THEO_*`, `LAST_*`. После рестарта эти данные теряются, поэтому
> `rebuildCache()` (`api/inc/mc.py`) пересобирает их при старте API и планировщика
> (задача #19): `PRICE/HV` заново берутся с Bybit, `LAST` — из Mongo `contracts`,
> `BEST` — из Mongo `orders`, `THEO` пересчитывается из `PRICE`/`HV`.

## 5. Как это работает (сценарии)

### 5.1 Регистрация

1. Пользователь жмёт **Gen Key** (`genKey()` в `exchange.js`) — генерируется ключ вида
   `XXXXX-XXXXX-XXXXX-XXXXX-X`.
2. **Gen Seed** делает `GET /seed` → Express возвращает случайную фразу (`routes/seed.js`, `sentencer`).
   Seed — это **мнемоника**, не секрет аутентификации.
3. Пользователь задаёт **пароль** (`#regPassword`) — это и есть секрет.
4. **Sign Up** → `POST /signup` на API. Сервер считает `hashUser(key)` (blake2b, 6 байт),
   сохраняет `seed` как есть, а пароль — только как `passwordHash`+`passwordSalt`
   (PBKDF2-HMAC-SHA512, 200k итераций). Начисляет 1000 Wei / 100 000 000 Satoshi.

### 5.2 Подпись запросов (HMAC)

Каждый торговый/приватный запрос подписывается **паролем** (не seed):

```js
// public/javascripts/exchange.js
shaObjHMAC.setHMACKey(password, 'TEXT');     // password — «секрет»
shaObjHMAC.update(question);                 // question — строка запроса
hmac = shaObjHMAC.getHMAC('HEX');            // SHA3-512 HMAC
```

Сервер: `checkUser(hash)` возвращает документ пользователя, `verifyPassword()` сверяет
PBKDF2, затем `checkHMAC(password, question, hmac)` (Python `hmac` + `sha3_512`).
Пароль приходит в теле каждого запроса — это **не** криптографическая защита, лишь
«проверка, что запрос пришёл от того же клиента». HMAC — симметричный, сервер знает
пароль в момент проверки.

### 5.3 Постановка ордера и матчинг

1. Фронт отправляет `POST /order` с `question = {action:'send', type, quant, asset, price}`.
2. `app.py:order()` проверяет HMAC и поля, вызывает `inc/trade.py:sendOrder()`.
3. `sendOrder()`:
   - проверяет достаточность средств (`checkOrder()` → `users.userBalances()`);
   - сравнивает свою цену с лучшей встречной (`getBestPrice`):
     - если невыгодно — ставит **лимитку** (`sendLimit()`);
     - если выгодно/равно — **сводит** с встречными заявками (`getLimit()`),
       для каждой пары создаёт сделку (`makeDeal()`), снимает/уменьшает встречный ордер;
   - остаток отправляет лимиткой;
   - обновляет Memcached (`upBest`, `setState`, `upLast`).
4. InfluxDB получает запись в «river» (`inOrder`/`inTrade`).

### 5.4 Расчёт баланса (`inc/users.py:userBalances`)

Итог = собственные средства
+ залоченные под продажу Call (base) / продажу Put (strike×qty, unit)
+ залоченные под покупку (unit)
+ реализованный P/L (`realisedPL`).

Формула возвращает дерево `{own, orders, contracts, prize, realised, available}`,
которое фронт рисует в блоке **Balances**.

### 5.5 Теоретическая цена

`inc/calculation.py` — Блэк–Шоулз без ставки (r = 0). Пересчитывается планировщиком
`api/theo.py` (отдельный сервис): раз в минуту (`setCurrent` → `setTheo`) и раз в
15 минут (`setHV`). При старте планировщик и API пересобирают кэш целиком
(`rebuildCache()`), поэтому свежий старт сразу отдаёт актуальные `THEO/BEST/LAST`
(задачи #18, #19).

**Требуют HMAC-подписи:**

| Метод | Путь | Тело |
|---|---|---|
| POST | `/signup` | `{key, seed, password, email}` |
| POST | `/user` | `{user, password, hmac, question}` — `question` ∈ `contracts\|orders\|trades\|balances` |
| POST | `/order` | `{user, password, hmac, question:{action:'send'\|'remove'\|'edit', ...}}` |

> HMAC считается по **паролю** (не по seed). Пароль передаётся в теле каждого
> запроса.
>
> **Единый формат ошибок (задача #16).** Любая ошибка API отдаётся настоящим
> HTTP-кодом (`400`/`401`/`404`/`409`/`429`/`5xx`) и телом
> `{"error": {"code": <int>, "message": <str>}}` — обработчик `@bottle.error`
> в `api/app.py`. Доменные ошибки из `inc/*` — через `inc/errors.py:ExchangeError`
> (например, нехватка средств → `400`).
>
> **Правка/снятие заявки (`/order`).** `remove` подписывается `'remove' + id`;
> `edit` — `'edit' + id + quant + price` (значения меняются, поэтому входят в
> подпись). Менять/снимать можно только **свою** заявку: чужая/несуществующая →
> `404`. `edit` выполняется под `tickerLock`, чтобы не гоняться с матчингом.
>
> `/signup`, `/user`, `/order` защищены **per-IP rate-limit** (задача #11):
> при превышении `RATE_MAX` за `RATE_WINDOW` секунд → **HTTP 429**. Настройки —
> `RATE_LIMIT`/`RATE_WINDOW`/`RATE_MAX` в `.env`; `api/inc/utils.py:rateAllow()`.
>
> **Graceful-поведение при недоступных хранилищах (задача #25).** Импорт
> `api/app.py` больше не падает, если Mongo/Influx/Memcached не подняты:
> `MongoClient`/`InfluxDBClient`/Memcached-клиент — ленивые, bootstrap
> (`loadCatalog`/`rebuildCache`) перехватывает ошибки. Чувствительные роуты
> (`/signup`, `/user`, `/order`, `/saldo`, `/orders`, `/river/*`) проверяют
> хранилища (`storageGuard`) и при недоступности отвечают **503**
> `{"error":{"code":503,...}}`; ошибки драйверов на горячем пути превращает в
> `503` декоратор `storageSafe`. Состояние видно в `GET /health`. Проверка
> кэшируется на `STORAGE_PROBE_TTL` секунд (см. `.env.example`), таймауты — `MONGO_SELECT_TIMEOUT`
> и `INFLUX_TIMEOUT`. Планировщик `api/theo.py` при ошибке тика не умирает.

5. **Node:** `npm install && node ./bin/www` (порт `WEB_PORT`, dev-дефолт 3000).

### 7.1. Запуск API/веба в фоне (важно для агентов)

🪨 **Симптом.** Если запустить сервер из инструментальной оболочки агента как
`python api/app.py &` (или `node ./bin/www &`), процесс живёт ровно до конца
команды: оболочка завершается, дочерний процесс из её process group получает
`SIGTERM` и умирает. В выводе это выглядит как `Killed by SIGTERM`, а затем
`curl` отдаёт `000` / `Failed to connect`. Каждый новый агент наступает на это
заново.

**Причина.** Инструментальная оболочка убивает всю группу процессов команды при
её завершении. `&` отвязывает только от терминала, но не от сессии/группы.

**Решение — отвязать процесс от сессии и закрыть все потоки:**

```bash
# API (выполнять из корня репозитория):
setsid nohup env PY_MODE=dev .venv/bin/python api/app.py \
  > /tmp/opencode/oe-api.log 2>&1 < /dev/null &

# Веб:
setsid nohup node ./bin/www > /tmp/opencode/oe-web.log 2>&1 < /dev/null &
```

- `setsid` — создаёт новую сессию/группу, процесс переживает завершение оболочки
  (это ключевое отличие от простого `&`).
- `nohup` — игнорирует `SIGHUP` (страховка), `</dev/null` — чтобы процесс не
  висел на stdin оболочки, `>log 2>&1` — логи в файл (`/tmp/opencode`, не в `#`
  агента, иначе они теряются).
- Хранилища (`docker compose up -d`) уже демонизированы — их так запускать не надо.

**Проверка, что процесс жив и не в этой сессии:**

```bash
pgrep -af "api/app.py"          # должен быть PID
curl -s -o /dev/null -w '%{http_code}\n' localhost:6969/counters/ETH_BTC   # 200
```

**Остановка / перезапуск:**

```bash
pkill -f "api/app.py"           # затем запустить снова командой выше
```

> Если `setsid` недоступен — минимально `nohup ... </dev/null >log 2>&1 &`.
> Альтернатива для «всё сразу» — скрипт из `docs/RUNBOOK.md` §10 (он использует
> тот же приём). Не полагайтесь на голый `&` в агентской оболочке.

## 10. С чего начать новому разработчику

1. Прочитать `README.md`, этот документ и **`docs/DONE.md`** (журнал уже сделанного).
2. Поднять стек (см. §7) и пройти сценарий: регистрация → баланс → ордер → сделка.
3. Открыть `views/exchange.pug` и `public/javascripts/exchange.js` — понять фронт стола.
4. Открыть `api/app.py` → `api/inc/trade.py` → `api/inc/users.py` — понять бэкенд.
5. Сверить изменения с `docs/SPEC.md`; закрытое фиксировать в `docs/DONE.md` (§0.4),
   не забывая про безопасность (§9).
6. После правок — прогнать `tests/e2e.py` и **дополнить его** проверками под свои
   изменения (§0.3.1). Не ослаблять существующие проверки.
